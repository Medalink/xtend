01

Intent, not lines

Each customization is a commit whose message says what you wanted. The agent reads those, so it rebuilds "dark, ring, 50 minutes" on top of the new code instead of picking hunks.

02

Both test suites decide

Upstream's tests came with the merge. xTend runs your check after every attempt and sends the failures back to the agent. Nothing is committed until it passes.

03

Or nothing changes

If three tries don't produce a clean, passing tree, xTend puts everything back as it was and exits non-zero. A failed sync never leaves a half-merge behind.

04 How it works

Five commands. Tools you already have.

xtend get owner/repo

Forks it on GitHub, clones it and writes the ref sheet. It also turns on a daily Action that runs xtend sync for you.

xtend "make it dark"

Your agent makes the change with the ref sheet in hand. Your check has to pass, and the commit message keeps what you asked for.

xtend sync

Merges upstream with git. When git can't finish, the agent does, guided by your intent. It retries until the check passes, or nothing changes.

xtend sheet

Reads the code and writes a short map for agents: layout, commands, where to extend, and which files churn.

xtend share

Shows what upstream accepts. Then it ports the changes you pick onto upstream's code and offers them the way the owner asks.

# pomo

## What it is
A Pomodoro timer that runs as one static web page, with no build step and no dependencies.
`timer.js` holds the timer logic as pure functions. Node tests import it, and the browser loads it as a global script.
`app.js` wires that logic to the DOM in `index.html`.

## Map
- `index.html`: page markup. Mode tabs (`[data-mode]`), `#time`, `#start` and `#reset`. Loads `timer.js` and then `app.js` as classic scripts.
- `timer.js`: `MODES` table, `createTimer(mode)`, `tick(t)` and `format(seconds)`. Exports them through `module.exports` only when `module` exists.
- `app.js`: browser controller. Keeps state in the `timer` and `interval` module-level variables. Defines `render()`, `setMode()`, `toggle()` and `step()`, plus the event wiring.
- `style.css`: all styling. Uses flat class selectors (`.card`, `.tabs`, `.time`, `.controls`, `.primary`, `.active`).
- `test.js`: plain `node:assert/strict` checks against `timer.js`. Prints `ok` when everything passes.
- `package.json`: `private`, one script (`test`), no dependencies.

## Build, run, test
- Test: `npm test`, which runs `node test.js`. Exit code 0 and the output `ok` mean pass. The first failing `assert` throws and exits non-zero.
- Run: open `index.html` directly in a browser. You can also serve the folder, for example with `npx serve .` or `python -m http.server`, and open `/`.
- Build: none. There is no bundler, no transpiler and no lint config.

## Extension points
- **New timer mode** (for example a long break):
  1. Add an entry to `MODES` in `timer.js`, for example `long: { label: 'Long break', minutes: 15 }`.
  2. Add `<button data-mode="long">Long break</button>` inside `<nav class="tabs">` in `index.html`. `app.js` binds every `[data-mode]` automatically.
  3. If the new mode should join the automatic cycle, change the transition in `step()` (`app.js`). It currently toggles only between `focus` and `break`.
- **Change durations**: edit `minutes` in `MODES`. Tests read `MODES.focus.minutes`, so they keep passing.
- **New pure logic** (session counter, cycle rules, formatting):
  - Add a function to `timer.js` in the same style as `tick`, which takes state and returns new state without mutating it.
  - Add the function to the `module.exports` object on the last line.
  - Add `assert` lines to `test.js` and destructure the new name in its `require`.
- **New button or control**:
  - Add an element with an `id` to `.controls` in `index.html`.
  - Bind it in `app.js` with `$('id').addEventListener(...)` next to the existing bindings.
  - Reflect any state it changes inside `render()`.
- **New displayed state**: add the DOM update to `render()`. `render()` is the only function that writes to the DOM.
- **Side effects when a session ends** (sound, notification): put them in `step()` inside the `if (timer.done)` branch. Keep them out of `timer.js`.
- **Styling**: add flat class rules to `style.css`. Reuse the palette that is already there (`#d9534f` accent, `#3b2f2a` text, `#f6f1eb` background, `#e5d9cf` borders, `#fbe9e7` active tint).

## Conventions
- Plain ES2015+ JavaScript in classic scripts. Do not use `import`/`export`, because `index.html` loads the files without `type="module"`.
- `timer.js` must stay free of DOM access and run in both Node and the browser. Keep the `if (typeof module !== 'undefined') module.exports = {...}` guard.
- `timer.js` and `app.js` share one global scope. Do not declare a top-level name in `app.js` that `timer.js` already uses, or the reverse.
- Treat state as immutable. Timer state is a plain object `{ mode, remaining, running, done }`, and updates use spread (`{ ...t, running: true }`).
- `remaining` is an integer count of seconds. Convert to text only with `format()`.
- The style has no semicolons, uses single quotes and 2-space indentation, and keeps short one-line conditionals.
- Look up DOM elements with the `$` helper, `const $ = (id) => document.getElementById(id)`. Select modes with `[data-mode]` and `dataset.mode`.
- Names are camelCase for functions and variables. `MODES` is the only constant in UPPER_CASE.
- Tests are flat `assert.equal(...)` statements in `test.js`, with no test framework. Add more statements and keep `console.log('ok')` as the last line.
- Add no dependencies. If you need one, add `devDependencies` to `package.json` and keep `npm test` working without a build step.

## Hot zones
History has one commit (`pomo 1.0`), which touched all six files once, so churn does not show where upstream will change next. All six files are small and likely to change upstream:
- `timer.js`: the core API (`MODES`, `createTimer`, `tick`, `format`) and the export line. Add new functions and `MODES` entries rather than changing the existing signatures or the shape of the state object.
- `app.js`: `step()` and `render()` are the likeliest places for upstream edits to collide with yours. Keep local behavior in separately named functions and call them with a single line from those two functions.
- `index.html`: keep the `<script>` order (`timer.js` before `app.js`) and the existing IDs (`time`, `start`, `reset`) unchanged. Add new markup as separate blocks.
- `style.css`: append local rules at the end of the file instead of editing existing rules.
- `test.js`: add assertions after the existing ones, before `console.log('ok')`. Do not rewrite the existing ones.
- `package.json`: keep the `test` script name and command, because the xtend check depends on `npm test`.

01

The owner decides

xTend reads XTEND.md, GitHub's settings and CONTRIBUTING.md before it builds anything. It quotes the line that says no, and stops. Nothing you pass overrides it.

02

Pick, don't merge

Each change is one commit on upstream's latest code, with the cherry-pick command under it. The owner takes one, some or all.

03

No floods

A person picks every change. xTend never offers from CI and keeps one open offer per project. It never re-offers what the owner closed, and opens at most 3 offers a day.
